# A suspension is told apart from other updates by the state the instance had before, and it is reported for every open task and for the case

This decision narrows one sentence of decision 3: "Anything else about the instance becomes an
update." An update which suspends or activates a process instance becomes a suspension or an
activation instead. Whoever merges this entry adds "except a suspension, see decision <n>" to that
sentence.

Decided on 2026-11-02. The cockpit now shows a suspended task and a suspended case. Only the reports
of a suspension and an activation change that, so a report this adapter misses is never healed by a
later one.

## What the engine does

Suspending or activating a process instance switches its executions and its tasks with bulk SQL
updates. No task listener runs. Then the command writes one history event `PROCESS_INSTANCE_UPDATE`
per instance, and the extension's history handler receives it. The same command runs for a process
definition with `includeProcessInstances(true)`, for a definition suspended at a later moment (from
a timer job), and for a batch, synchronous or asynchronous. A definition suspended without its
instances changes no instance and writes no event, so nothing is reported, which is right.

## How a suspension is recognized

Every update of an instance carries its state, also one which only gave it a business key or moved
it to another version of its process. So the state alone does not say that the suspension changed.

The engine runs a bulk update when the command ends. Up to then the instance the command holds still
has its old state. That is why the suspension command writes the new state into the history event
itself, and every other update takes the state from the instance. So the handler compares the state
of the event with the state of the instance the command holds. Where they differ, the suspension
changed. Where they are the same, the event is an ordinary update.

The class of the running command was the other candidate. It does not work for the timer and the
asynchronous batch: both run the suspension command inside the command of the job, so the running
command is the job's.

The comparison also leaves out an instance whose state stays. A definition suspended with its
instances updates every instance, also one somebody suspended before. That one is not reported
again, so it keeps the moment and the person of its own suspension.

## What is reported

- Every open user task of the instance: `SUSPENDED` or `ACTIVATED`, through
  `publishUserTaskSuspension`. The task is found by its process instance id, so the tasks of a
  called instance are not reported. The engine does not suspend a called instance together with its
  caller. A task is reported only where the extension's own task listener sits on its element. The
  listener knows the identifiers the task is reported with everywhere else.
- The workflow, where the instance is a case of its own (decision 3): `SUSPENDED` or `ACTIVATED`,
  through `publishWorkflowSuspension`. A step of its caller's case reports its tasks and no
  workflow, because the case is not suspended.
- No update. Before this decision a suspension reached the cockpit as an update of the workflow.
  The update asked the details provider about data nobody changed.

Each report is written into the engine's transaction like every other report. It reaches the
cockpit if and only if the suspension was committed.

The person is the user signed in on the thread which runs the command:
`CommandContext.getAuthenticatedUserId()`. It goes out as the initiator of the report, and the
cockpit stores it as `suspendedBy`. Nobody is signed in in the job executor, which runs the timer
and the asynchronous batch, nor in a REST call without authentication. Those reports carry no
person. The user operation log is no better source: it needs the history level `full`, and by
default it is written only for a signed-in user anyway.

The moment is the engine's clock (`ClockUtil`) when the handler runs. The engine stores no moment
of a suspension. The engine has no id of its own for a suspension either, so the event id names the
task or the workflow, the kind and that moment.

The prefilled details stay without `suspendedAt` and `suspendedBy`. The engine knows only whether
an instance is suspended, not since when or by whom.
