# Only a deletion hands its delete reason to the cockpit, and a run the engine tore down is cancelled

Decided on 2026-11-13 by the maintainer.

## What the extension does

A workflow is cancelled where its process instance ended without a token reaching an end event. The
engine writes that into the state of the history event of the end: `COMPLETED` for a run which reached
an end event, `EXTERNALLY_TERMINATED` or `INTERNALLY_TERMINATED` for a run it tore down. Which of the
two depends on a flag the caller may pass, and the Java API passes `false` by default. So both count.
A deletion without a reason is cancelled as well. Up to now only a deletion with a reason was, because
the engine writes no delete reason where nobody gave one.

The delete reason becomes the comment of the workflow and of its user tasks only where the end is a
deletion: while the engine runs a command which deletes process instances, or a job of a batch which
deletes them. The Camunda web application and the REST API use the same command. A details provider
which sets a comment of its own replaces it.

## Why the running command decides for a user task

The engine deletes the tasks of a process instance first and marks the instance as deleted only
afterwards. So while the task listener runs, the instance looks the same as for a task a boundary event
takes away. The command the engine runs is the only thing which tells a deletion apart. It is the same
for a nested call and for a call of the REST API. A batch runs the command inside its own job, so the
job is what is asked for there.

The engine gives a task the word `deleted` where the person gave no reason. That word is the engine's
stand-in for "none" and is no comment.

## What is no deletion

A boundary event, an interrupting event subprocess and a terminate end event end the run on an end
event of the model. The workflow is completed and nothing gets a comment. A process instance
modification which cancels the last activity tears the run down, so the workflow is cancelled, but it
is no deletion and gets no comment. The same holds for a called process with a workflow aggregate of
its own, which the engine tears down because a boundary event interrupts the call activity of its
caller.
