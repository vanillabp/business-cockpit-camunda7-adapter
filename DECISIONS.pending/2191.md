# The extension depends on the extension SPI, and the adapter SPI only for one question

**Status:** decided, 2026-11-21, story 2191, the follow-up of the same story of
`adapter-platform-integration` (its `DECISIONS.pending/2191.md`) and of `business-cockpit` (its
`DECISIONS.pending/2191.md`). No entry of this log is superseded. Decision 3 and decision 14 still
name `WorkflowTaskWiring`, and both are still true: the extension still takes that bean.

The extension used to read four types from the core of VanillaBP and the adapter SPI:
`MigrationAdapterProperties` for the configured adapter ids, `NameClashAvoidanceSupport` for how an
engine spells a process id, `MultiInstanceValue` for one iteration of a multi-instance element, and
`WorkflowTaskWiring` for two questions about what the application declared. None of them was a
promise to an extension.

The platform now offers what an extension needs in its SPI artifacts, and the extension uses that:

- `VanillaBpSettings` of the extension SPI answers `adapterIdsOfType`. The Quarkus producer takes it,
  and the Spring Boot auto-configuration waits for a bean of that type.
- `IdentifierScoping` of the integration SPI answers `SEPARATOR` and the static `scopedProcessId`.
  `Camunda7Scope` and `Camunda7CockpitCustomizer` take it.
- `MultiInstanceIteration` of the integration SPI is what `Camunda7CockpitBridge` reads from the
  map of `Camunda7MultiInstances.of`.

`WorkflowTaskWiring` stays, in `Camunda7CockpitWiring`, `Camunda7WorkflowProcesses` and the two
platform modules which hand it over. `WorkflowTaskClaims` of the integration SPI answers
`isClaimedByAWorkflowService`, but not `workflowsShareTheWorkflowAggregate`. Decision 3 asks the
core exactly that question. When the platform adds it to `WorkflowTaskClaims`, the field and the
constructor parameters change to that type, and the core module no longer declares the adapter SPI.

The POMs follow. `migration-adapter` is a test dependency of the core module only. The core module
declares `vanillabp-adapter-spi` for the reason above. The Spring Boot module declares
`vanillabp-spring-boot-integration` for `AdapterBeanRegistrarSupport#forEachConfiguredAdapterId`,
which the platform allows: it is asked while beans are registered, before `VanillaBpSettings` is a
bean.

An enforcer rule `an-extension-depends-on-the-extension-spi-alone` in the root `pom.xml` bans
`migration-adapter`, `vanillabp-adapter-spi`, `vanillabp-spring-boot-integration` and
`vanillabp-quarkus-integration` in the scopes `compile`, `provided` and `runtime`. It is the rule of
`extensions-commons`, with one difference: it checks only what a module declares
(`searchTransitive=false`). The Camunda 7 adapter is a BPMS adapter. Its core module depends on the
adapter SPI, and its platform modules depend on the platform integrations, on purpose. A transitive
ban would ban the adapter this extension plugs into, and excluding those artifacts would break the
adapter at runtime. The core module and the Spring Boot module each take one artifact out of the
ban, with `combine.self="override"`, and the comment at the dependency says why.

Referred to by: the root `pom.xml` (the enforcer rule), `core/pom.xml`, `spring-boot/pom.xml`,
`AGENTS.md` (section "This is an extension, not a BPMS adapter"), the Javadoc of the field `core` in
`Camunda7WorkflowProcesses`.
